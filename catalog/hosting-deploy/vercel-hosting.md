# Vercel Hosting

- **category**: hosting-deploy
- **provider**: Vercel
- **reusable**: partial — the underlying pattern (link a repo, deploy via git integration, mirror env vars, optionally pin a region) is identical across every repo, but the actual config is per-project and not a shareable code package; worth a shared deploy-checklist rather than an extraction.
- **docs**: https://vercel.com/docs

## Overview
Vercel is the git-integrated build/hosting/CI-CD platform used as the default production target for every Next.js (and one Vite) app in this marketplace. Deploys are triggered by pushing to the linked GitHub repo; project identity and behavior are controlled by `.vercel/project.json` (auto-generated by `vercel link`) and an optional `vercel.json` (region pinning, framework override, build/output overrides, cron jobs).

## Playbook

### Prerequisites
- A GitHub (or GitLab/Bitbucket) repo containing the app.
- A Vercel account/team with permission to import projects.
- All required env vars collected from `.env.local` (names only — see below).

### Setup steps
1. Push the app to its git remote.
2. In the Vercel dashboard: **New Project → Import** the repo (or run `vercel link` from the repo root to link an existing Vercel project non-interactively — this writes `.vercel/project.json`).
3. **Framework Preset**: for a Next.js app, explicitly confirm/set the preset to "Next.js" in Settings → Build and Deployment. Leaving it as "Other" (which can happen on import, especially in a monorepo) silently makes every route 404 at runtime rather than failing the build — there is no build-time signal that this is wrong.
4. For a non-Next static build (e.g. Vite), add a `vercel.json` declaring `framework`, `buildCommand`, and `outputDirectory` explicitly rather than relying on auto-detection.
5. In a monorepo, add a per-app `vercel.json` inside the app's subdirectory (e.g. `apps/web/vercel.json`) with explicit `framework`/`buildCommand`/`installCommand` — Vercel's Turborepo auto-detection runs a root-level install across all workspaces first, then this file governs the specific app's build. Confirm every import used by app code is actually declared in that workspace's `package.json`, not just present in a stale local `node_modules` — a clean CI install will drop anything undeclared and fail with `Module not found`, which will not reproduce locally.
6. Copy every required env var name from `.env.local` into the Vercel project's Environment Variables settings, for both **Production** and **Preview** (and Development if you use `vercel dev`).
7. If the deploy needs a fixed region (e.g. to colocate with a regional database), add `"regions": ["<region>"]` to `vercel.json`.
8. Deploy (push to the linked branch, or `vercel --prod`).

### Core pattern
Root-level `vercel.json` — pin a region:
```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "regions": ["fra1"]
}
```

Static build (non-Next framework, e.g. Vite) — explicit build override:
```json
{
  "framework": "vite",
  "buildCommand": "npm run build",
  "outputDirectory": "dist"
}
```

Monorepo per-app override (placed at `apps/web/vercel.json`, discovered by Vercel's Turborepo auto-detection after the root install):
```json
{
  "framework": "nextjs",
  "buildCommand": "next build",
  "outputDirectory": ".next",
  "installCommand": "npm install"
}
```

`.vercel/project.json` (auto-generated by `vercel link` — do not hand-write; commit it so the whole team/CI shares the same linked project):
```json
{
  "projectId": "prj_xxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "orgId": "team_xxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "projectName": "<project-name>"
}
```

Guarding a Vercel Cron-invoked route with a shared secret (standard pattern for any endpoint a `crons` entry in `vercel.json` hits — validate before relying on it against the actual deployed route, since it must both be declared in `vercel.json`'s `crons` array and checked inside the handler):
```ts
export async function GET(req: Request) {
  const auth = req.headers.get("authorization");
  if (auth !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("Unauthorized", { status: 401 });
  }
  // ... cron work ...
}
```

### Env vars
- `VERCEL_OIDC_TOKEN` — auto-injected by Vercel into every deployed function; used for workload identity, not something you set yourself.
- `CRON_SECRET` — only needed if a `vercel.json` `crons` entry hits a route that self-validates the caller.
- Every app-specific `NEXT_PUBLIC_*` and server-side env var must be mirrored into the Vercel project's Environment Variables UI — Vercel does not read `.env.local` at build/runtime.

### Gotchas
- **Framework Preset defaults to "Other" silently** in some import flows — this doesn't fail the build, it makes every route 404 at runtime, which is a much harder failure to diagnose than a build error.
- **`.vercel/` linkage without a `vercel.json` is a valid, common state** — a repo can be fully deployed via Vercel with zero explicit config, relying entirely on framework auto-detection; absence of `vercel.json` is not evidence the integration isn't real (check for `.vercel/project.json` too).
- **A README mentioning "Deploy on Vercel" is not evidence of an actual deployment** — `create-next-app`'s boilerplate README includes that section unconditionally; only `.vercel/project.json` or a real `vercel.json` confirms an actual linked, configured deployment.
- **Monorepo builds run a root install first, then a per-app build** — a dependency imported in app code but only present in `node_modules` (never added to that workspace's `package.json`) works locally but breaks on Vercel's clean CI install with `Module not found`.
- **A platform migration attempt can leave no trace once abandoned** — one repo in this marketplace spiked a Cloudflare Workers migration and reverted it after hitting a hard SDK incompatibility (see `firebase-admin-sdk.md`); the only remaining evidence was in a CLAUDE.md note, not in any deploy config. Don't assume a single Vercel config file is the complete deployment history.
- **A `crons`-invoked endpoint's secret only protects the route if the route handler actually checks it** — declaring `CRON_SECRET` as an env var name in a catalog entry is not proof the check exists in current code; verify against the live route before relying on it.

### Playbook confidence: high

## Adoption
Used in **7** repo(s) in this marketplace. Most adopt it as a plain Next.js production hosting/CI-CD target with no more than region pinning; other shapes seen include a static Vite build deployed as the build output, a monorepo linking one app via a per-app config, a Vercel Cron-invoked endpoint guarded by a shared secret, and a project linked via the CLI with no explicit config at all (pure framework auto-detection). One adopter's evidence turned out to be boilerplate scaffold text with no actual linkage or config present — a reminder that a deploy-target mention in a README isn't proof of a real integration. Another had briefly evaluated migrating to a different hosting platform before reverting back to this one.
