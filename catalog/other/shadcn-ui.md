# shadcn/ui component registry

- **category**: other
- **provider**: shadcn
- **reusable**: partial — the `components.json` config shape and the "own the generated code" workflow are portable to any Next.js + Tailwind project, but it's a build-time scaffolding tool, not a runtime external-service dependency (no live network calls, no API keys).
- **docs**: https://ui.shadcn.com/docs/components-json and https://ui.shadcn.com/docs/cli

## Overview
shadcn/ui is a CLI-driven component registry: running `npx shadcn add <component>` copies a component's source (not a package dependency) directly into the project under `components/ui/`, styled with Tailwind and configured via `components.json`. There's no runtime network call, hosted service, or API key — it's a code-generation/scaffolding tool used at development time only.

## Playbook

### Prerequisites
- A Next.js (or similar) project with Tailwind CSS already configured.
- Node/npm available to run the `shadcn` CLI.

### Setup steps
1. Run `npx shadcn@latest init` in the project root; answer the prompts (style, base color, RTL, TypeScript, CSS file path, import aliases).
2. This generates `components.json`, which records the chosen style, Tailwind config path, CSS file, icon library, and path aliases (`components`, `utils`, `ui`, `lib`, `hooks`) so future `add` commands know where to place generated files.
3. Add a component with `npx shadcn@latest add <component-name>` (e.g. `button`, `dialog`) — this copies the component's source into `components/ui/<name>.tsx`, wired to the project's existing `cn()` utility and design tokens.
4. Customize the generated component files directly — they are owned project code, not an upgradable dependency; there is no "update package" step, only re-running `add` (which may overwrite local edits) or hand-editing.
5. If the project supports RTL, set `"rtl": true` in `components.json` so generated components include RTL-aware classes.

### Core pattern
```json
// components.json — generated by `npx shadcn@latest init`, read by every subsequent `add`
{
  "$schema": "https://ui.shadcn.com/schema.json",
  "style": "base-nova",
  "rsc": true,
  "tsx": true,
  "tailwind": {
    "config": "",
    "css": "app/globals.css",
    "baseColor": "neutral",
    "cssVariables": true,
    "prefix": ""
  },
  "iconLibrary": "lucide",
  "rtl": true,
  "aliases": {
    "components": "@/components",
    "utils": "@/lib/utils",
    "ui": "@/components/ui",
    "lib": "@/lib",
    "hooks": "@/hooks"
  }
}
```

```bash
# Scaffold a new component into components/ui/
npx shadcn@latest add button
```

### Env vars
none — build-time CLI tool, no runtime configuration or API keys. (A private/custom component registry, if used, would need its own registry-URL/token config, but the default public registry needs none.)

### Gotchas
- Generated components are **copied source**, not an npm dependency you `npm update` — there is no version-drift protection; re-running `add` on an already-customized component can silently overwrite local changes.
- `components.json`'s `aliases` must match the project's actual TypeScript path aliases (`tsconfig.json` `paths`) or generated imports will fail to resolve.
- Because there's no runtime network call, this integration produces zero attack surface or outage risk at runtime — it's purely a dev-time scaffolding convenience, unlike the rest of this catalog which tracks live external dependencies.
- If `rtl: true` is set but the project's actual CSS isn't RTL-aware end-to-end, some generated components may render RTL utility classes that have no visible effect, giving a false sense of RTL support.
